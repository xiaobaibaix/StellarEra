## 构建与编译

- **不用 `Build.bat`，用 dotnet 直调 UBT。** `Build.bat` 的句柄重定向（`9>&2 2>nul (call ...)`）毒化子进程，UBT 必报 `Unable to find project file based on argument`。
- 可靠命令（2026-10-13 验证 `Result: Succeeded`，cwd 须在项目外）：`D:/Application/Epic Games/UE_5.8/Engine/Binaries/ThirdParty/DotNet/10.0/win-x64/dotnet.exe D:/Application/Epic Games/UE_5.8/Engine/Binaries/DotNET/UnrealBuildTool/UnrealBuildTool.dll StellarEraEditor Win64 Development -Project=F:/workspace/ue/StellarEra/StellarEra.uproject -WaitMutex -FromMsBuild`。
- **构建前必须关编辑器。** Live Coding 活动时 UBT 退出码 6：`Unable to build while Live Coding is active. Exit the editor and game, ...` / `Result: Failed (OtherCompilationError)`。`Ctrl+Alt+F11` 只在改函数体时可用；改**构造函数里的组件默认值**（`CreateDefaultSubobject` 之后的赋值，如 `SpringArm->bInheritRoll`）时它不重跑构造函数、不刷新 CDO，会「编译成功但行为没变」。
- **`Result: Failed` 不代表没编过。** UBT 先出 `.obj`、链出 `UnrealEditor-StellarEra.lib`，最后写 `Binaries/Win64/UnrealEditor-StellarEra.dll` 才失败（UBA 报 `used by another process`，退回 `[NoUba]` 后是 `LNK1104`）。判据比 mtime：`.obj`/`.lib` 新、`.dll` 旧 ＝ 编译通过只差链接；此时 DLL 仍是旧的，不能拿去测。
- **「编辑器开着」不能用 `tasklist` 判断。** bash 沙箱里 `tasklist | grep UnrealEditor` 返回空但编辑器还活着（Live Coding 判定靠命名互斥体 `Global\LiveCoding_<可执行文件全路径，/\: 换成 +>`）。用 `powershell.exe -NoProfile -Command "Get-Process | Where-Object { $_.ProcessName -match 'UnrealEditor' }"`，杀进程 `Stop-Process -Force`（连同 `LiveCodingConsole`），杀前先问。bash 对 D: 盘的视图间歇性消失，D: 上的操作走 PowerShell。
- **worktree 隔离会话里 Bash 护栏拒掉带空格的绝对路径当命令名**（`command whose name is computed at runtime` / `too complex to verify`），`cmd //c` 与管道同样被拒。绕过：塞进 PATH 再用裸名 —— `PATH="/d/Application/Epic Games/UE_5.8/Engine/Binaries/Win64:$PATH" UnrealEditor-Cmd.exe <args>`；UBT 用 PATH 上的 `dotnet`（系统 10.0.401 能跑 5.8 的 UBT.dll）。
- **MSB4018「SetEnv 任务意外失败」**：UE 5.8（引擎 D:、项目 F: 跨盘）生成的 vcxproj `<IncludePath>` 约 32.4K 字符，MSBuild 的 `SetBuildDefaultEnvironmentVariables` 设为 INCLUDE 时超 Windows 32767 上限，报 `ArgumentException 环境变量名或值太长`。只有 VS/MSBuild 崩，2026-10-11 启用 VisualStudioTools 后首次触发。修复是项目根 `Directory.Build.props` 设 `<UseEnv>true</UseEnv>` —— **但 2026-10-14 核实已不存在**（`git log --all -- Directory.Build.props` 从未提交过）。**再报就重建它**。
- **CLion 报 `cmake_minimum_required` 兼容错**：根 `CMakeLists.txt` 由 UBT 的 `CMakefileGenerator.cs`（`-CMakefile`，CLion 打开 .uproject 时触发）生成，写死 `cmake_minimum_required (VERSION 2.6)`，CLion 2026.2 自带的 CMake 4.3.1 已移除 <3.5 兼容。即时修：第 4 行改 `(VERSION 3.5)`；持久修：CMake options 加 `-DCMAKE_POLICY_VERSION_MINIMUM=3.5`（UBT 重生成会打回 2.6）。真正构建走 `StellarEraEditor` 等 target。
- **无头跑材质生成器时 `QUIT` 不生效。** `UnrealEditor-Cmd -ExecCmds="StellarEra.BuildXxxMaterial,QUIT"` 执行成功但进程不退出，锁住 `Binaries/Win64/UnrealEditor-StellarEraCelestial.dll`，下次 Link 报 `LNK1104` / UBA `ERROR opening file ... for write`。跑前 `tasklist | grep UnrealEditor-Cmd` 查冲突，跑后按 PID `taskkill //F //PID <pid>` 复查；判据是日志 `材质已生成：<路径>` + `ls -la` 看 uasset 字节数变了。

## IntelliSense 与 IDE

- **IDE 是 VS Code，没有也不该有 `.vcxproj` / `.sln`。** `UBT -projectfiles` 生成 `StellarEra.code-workspace` + `.vscode/compileCommands_{StellarEra,Default}.json`（同目录带 .rsp）；项目里不存在 `Intermediate/ProjectFiles/*.vcxproj`、`*.slnx`、`*.sln`，`.gitignore` 也忽略它们，这不是缺失。机器上装了 VS 18（`D:\Program Files\Microsoft Visual Studio\18\Community`）但 UE 5.8 的 UBT 认不出，故落到 VS Code 格式。2026-10-12 23:26 从 VS 迁来，`sync_vs_project.py` 钩子与 vcxproj 一并撤掉；判断「是不是弄丢了东西」看**目录 mtime**。
- **含中文的源文件必须 UTF-8 with BOM。** 中文 Windows（cp936）下无 BOM 的 UTF-8 被 IntelliSense 按 GBK 读，`UMETA(DisplayName="中文")` 行全标红、约 20 个假错，而 UBT 全绿（cl.exe 自带 `/utf-8`）。修法是字节级前置 `EF BB BF`，**这一道够用**：2026-10-14 在 DLL 里按 UTF-16LE 搜 `按 E 登船` / `按 E 离船` / `找不到角色模型` 全命中。第二道保险（`Directory.Build.props` 加 `/utf-8`）已随该文件消失。红波浪线真假先看 UBT 结果。
- **只有新建目录的头报「无法打开源文件」（C/C++ 1696）＝ 编译数据库过期，不是索引坏。** cpptools 对 `.cpp` 用 `compileCommands_StellarEra.json` 里 `cl.exe @xxx.rsp` 的 `/I`，rsp 是生成时的目录快照，Build.cs 的递归循环只在重生成工程文件时展开目录。确诊：rsp 的 `/I "..."` 目录集合与 `Source/**` 下含头的目录求差。修法：`UnrealBuildTool.exe -ProjectFiles -Project=... -Game -Engine -Progress -VSCode`，再 `python Tools/vscode_intellisense.py`（UBT 会覆盖 `c_cpp_properties.json`）。
- 读 rsp 顺着 compileCommands 条目里的 `@路径` 找，**rsp 每次重生成会重新编号**，别缓存文件名。cpptools 会自己重解析。副作用：UBT 会往 tracked 的 `.ignore` 里加行。

## 编辑器 MCP

- **端点 `http://127.0.0.1:8000/mcp`**（Epic 官方 ModelContextProtocol 插件，HTTP streamable，`-ModelContextProtocolPort=N` 可覆盖）。**端口 1985 是 UE Trace 控制通道**，别被 netstat 骗。bash 沙箱**不拦本地回环**：`urllib.request.urlopen('http://127.0.0.1:8000/mcp')` 拿到 405。日志时间戳是 UTC（比本地早 8 小时）。
- 握手：POST initialize（`Accept: application/json, text/event-stream`）→ 取响应头 `mcp-session-id` → notifications/initialized → 之后带该 session 头。编辑器重启后会话失效（404），重新 initialize。**协议头必须带服务端返回的 `2025-11-25`，带 2025-03-26 会 400。**
- 结构：只有 3 个元工具 `list_toolsets` / `describe_toolset` / `call_tool`，真实工具按 toolset 组织（40+ 个）。**`call_tool` 必须传短名 + `toolset_name`**（如 tool_name=`get_dependencies`、toolset_name=`editor_toolset.toolsets.asset.AssetTools`），传全名报 `Tool not found`；ProgrammaticToolset 沙箱内的 `execute_tool()` 要传全名。沙箱只能 import `math/json/time/re/datetime/copy`，**没有 `unreal` 模块**。
- 需要内容浏览器 UI 响应的工具（如 EditorAppToolset.SelectAssets）在编辑器不在前台时报 `Timed out waiting for asset selection`（后台 3FPS 节流）。game thread 饱和时（体素生成时）MCP 调用超时，编辑器 `Responding=True`，等一会重试。日志：`Saved/Logs/StellarEra.log`。
- **多 worktree 并存时 8000 只有一个赢家**：后起者日志 `LogHttpListener: Error: HttpListener unable to bind to 127.0.0.1:8000`，但 MCP 调用照样「成功」—— 回答的是**另一个 worktree 的编辑器**。判据：返回值 `signal_file_path` 指向的目录不是你当前 worktree（如 `worktrees/planet-water`），或报的属性在你的代码里明明存在。先 `netstat -ano | grep ":8000" | grep LISTENING` 拿 PID，不是刚起的就 taskkill 重起。
- **VibeUE 是挂在同一 8000 端点上的扩展**，注册为 `VibeUE.*` toolsets（30+ 个），顶层另多出 `execute_python_code`、`capture_image`、`deep_research`、`terrain_data`。源码在 `Plugins/VibeUE`，UBT 直调编译 233s 成功。
- 自动启动：`Config/DefaultEditorPerProjectUserSettings.ini` → `[/Script/ModelContextProtocolEngine.ModelContextProtocolSettings]` 设 `bAutoStartServer=True`、`ServerPortNumber=8000`。项目根 `.mcp.json` 写 `unreal-mcp` → 该 URL。`execute_python_code` 是主力（批量多步、直接调 `unreal.*`，`auto_save` 默认 true）。脚本 `%TEMP%\ue_mcp\mcp_call.ps1`（含 UTF-8 BOM，否则 PS5.1 按 GBK 读碎中文注释）与 **`%TEMP%\ue_mcp\uemcp.py`**（`python uemcp.py sandbox <脚本.py>` / `tool <短名> <json> <toolset>`）。

## 编辑器进程与 Tick

- **编辑器不在前台时整进程（含 PIE）硬限 3 FPS**：日志 `LogWorld: Bringing World ... up for play (max tick rate 3)`，切前台立刻 `max tick rate 60`。源码 `UEditorEngine::GetMaxTickRate` 在 `ShouldThrottleCPUUsage()` 为真时 `MaxTickRate = 3.0f;`，读的是 `UEditorPerformanceSettings::bThrottleCPUWhenNotForeground`（默认 `true`）。实测同一次 PIE：前台体素生成 0.16~3.8 秒，后台 179.77 秒。测性能前确认前台；关节流：偏好 → 性能 → 取消「未在前台时节流 CPU」，或 ini 写 `[/Script/UnrealEd.EditorPerformanceSettings] bThrottleCPUWhenNotForeground=False`。
- 同一设置的另一个表现：**后台时编辑器世界按 `LEVELTICK_TimeOnly` 推进，所有组件 Tick 停摆，`bTickInEditor=true` 也救不了。** `UEditorEngine::Tick` 给每个视口 `AddRealtimeOverride(false, "Background Process")` → `IsRealtime=false` → `TickType=LEVELTICK_TimeOnly`；`UWorld::Tick` 里 `bDoingActorTicks` 只在非 TimeOnly 时为真。`GetRealTimeSeconds()` 照涨，拿它当「世界在 Tick」的证据会误判，要用 `GetTimeSeconds()` 或组件自己的 Verbose 行。
- **编辑器不能在 SSH / 服务会话里启动。** 进程落在会话 0，建视口时 `Fatal error ... WindowsD3D12Viewport.cpp:162 DXGI_ERROR_NOT_CURRENTLY_AVAILABLE` 直接崩；编译无此问题。做法：`qwinsta` / `query user` 找 console 会话 → .bat `start "" "<UE>/Engine/Binaries/Win64/UnrealEditor.exe" "<项目>/StellarEra.uproject"` → `schtasks /create /tn Xxx /tr "<bat>" /sc once /st 23:59 /it /f`，`schtasks /run /tn Xxx`，跑完 `schtasks /delete /tn Xxx /f`；验证 `Get-Process UnrealEditor | Select Id,SessionId` 为 1。

## 验证与调试流程

- **用户报「没反应」第一件事查 DLL，不是提假设。** 截至 2026-10-17 已两次，真因都是代码没编译进 DLL。① `ls -l` 比 `Source/**` 与 `Binaries/Win64/UnrealEditor-*.dll`。② `grep -a -c '<符号名>' <dll>` —— **只有 UPROPERTY / UCLASS / UFUNCTION 进反射字符串表**，纯 C++ 私有成员（`BaseArmLength`、`ForwardSpeed`、`ThrustInput`）恒为 0，拿它们当「没编译」的证据会误判；用已知 UPROPERTY 当正对照。回复要说清「编译完成前这个功能一定没反应」。

## Git 与 LFS

- **`Content/` 与拆分文件常驻暂存区，`git add <路径>` 后再裸 `git commit` 会吞掉全部。** `git add` 只往索引里加你那份，不缩小范围；`git commit` 不带 pathspec 提交的是**整个索引**。索引文件数会变（见过 179 与 1），先跑 `git diff --cached --name-only | wc -l` 看当前值。踩过：裸 commit 一次吞掉 180 个文件（之后该数由 179 变 0，`git show --numstat HEAD` 列出全部 `Content/**` 与 `Source/{StellarEra => StellarEraX}/**` 重命名），靠 `git reset --soft HEAD~1` 回退重提。
- 提交一律 `git commit -m "…" -- <显式全路径>`，提交后核验三件：① `git show --numstat --format="" HEAD | wc -l` == 本次改动文件数；② `git diff --cached --name-only | wc -l` 与提交前相同；③ `git rev-parse --short HEAD^` 是预期父提交。
- **`git merge` 报 `local changes ... would be overwritten by merge` 指向某个 `Content/__ExternalActors__/**/*.uasset`（状态 `AM`）时不一定真冲突**：索引里有预存暂存新增（HEAD 和两个分支都没有该路径），ort 策略保守拒绝。不能直接 `git restore --staged` 再 `git add`（会把暂存内容替换成工作区版本）。做法：① `git merge-tree --write-tree HEAD <branch>` 拿树，`git ls-tree <tree> -- <path>` 空输出即安全；② `SHA=$(git rev-parse :<path>)`（冒号取索引版本）；③ `git restore --staged -- <path>`；④ `git merge --no-ff <branch> -m "..."`；⑤ `git update-index --add --cacheinfo "100644,$SHA,$path"` 放回；⑥ `git status --porcelain` 应恢复成 `AM`。
- **更糟：静默 auto-stash 后 unstash 失败。** 74 个纯 `A` 时 `git merge` 不拒绝，把索引塞进内部 stash（dangling merge commit），`git merge-recursive` 删工作区文件时 16 个被编辑器占用报 `Invalid argument`、其余 58 个被真删，最后 `Index was not unstashed` 中止并把索引留在 HEAD —— `git status` 看着干净，资产已从磁盘消失。恢复：找那条 stash merge commit（`git fsck --unreachable` / reflog，`git show -s --format=%P <sha>` 有两个父），**第二父 `<sha>^2` 就是原索引树**（内部 stash 不进 `git stash list`）→ `git read-tree <sha>^2` → `git diff --cached --name-only HEAD > /tmp/added.txt` + `git checkout-index -f --stdin < /tmp/added.txt` 写回 → 记 `git ls-files --stage` → `git read-tree HEAD` 后再合并 → 逐行 `git update-index --add --cacheinfo "<mode>,<sha>,<path>"` 放回 → 确认只剩 `A`。
- **日志里成片的 `LogAssetRegistry: Error: Package is unloadable: Invalid value for PACKAGE_FILE_TAG` 是未 smudge 的 LFS 指针文件，不是资源损坏。** 指针 129 字节（`version https://git-lfs.github.com/spec/v1` + `oid sha256:…` + `size N`）。机械确诊：报错条数 == 磁盘上 LFS 指针资源文件数（2026-10-18 实测 378 ↔ 378），`find Content Plugins -type f \( -name '*.uasset' -o -name '*.umap' \) -print0 | xargs -0 grep -la "version https://git-lfs" | wc -l`。根因：LFS 规则 `14409d9`（2026-10-17）不回溯重刷已 checkout 的文件。指针覆盖的不只是插件：`Content/__ExternalActors__/Maps/UniverseMap/1/E3/X8S6…uasset` 是**两颗体素行星之一**，加载失败那行星不进关卡，星图测试误读成「只显示一个天体」，**测试前先查**。
- 修复 `git lfs checkout`（`.git/lfs/objects` 齐全不需联网，实测 617 对象 / 747 MB / 0 缺失）；修前验样本：指针 `size N` == `.git/lfs/objects/<前2>/<次2>/<oid>` 字节数，对象头四字节 `c1832a9e`（UE 的 `PACKAGE_FILE_TAG`）。非破坏性，`git status` 修前修后都为空（clean filter 会换算回指针），别拿它当「没改动」的证据。
- **GitHub `github.com:443` 直连超时**，SSH 可通，远端 `origin` 是 `git@github.com:xiaobaibaix/StellarEra.git`。`git push` 的 ref 走 SSH 没事，但 LFS 的 batch/上传走 HTTPS，不挂代理会卡在 `git lfs pre-push`：`HTTPS_PROXY=http://127.0.0.1:7897 HTTP_PROXY=http://127.0.0.1:7897 GIT_SSH_COMMAND="ssh -o BatchMode=yes -o ConnectTimeout=15" git push -u origin <branch>`。端口来自系统代理（当前 `127.0.0.1:7897`），变了查 `reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings" /v ProxyServer`。首次推送 645 个 LFS 对象、约 897 MB。不要把 PAT 写进 remote URL。
- **GitHub LFS 额度：Free / Pro 均 10 GiB 存储 + 10 GiB/月带宽**，旧资料「免费 1 GB」已过时。数据包已取消改按量计费，定价页仍标 `$5 / 50 GB`（≈ $0.10/GiB）。超额看 budget：`budget = $0` 不扣费但 LFS 封到月底；删 budget 不限额按量扣费；无付款方式超存储只能拉不能推。**上传只计存储不计带宽**。每版本永久计存储（同一 `.uasset` 改 1 字节再推仍按整文件再计）。**删文件 / 改写历史不退配额**，只能删库重建或找 Support。本仓库首次推送 897 MB ≈ 10 GiB 的 9%。
- **UE 提交前校验在 Git provider 下必然报「此变更列表中缺失 X（引用自 Y）」，是结构性假阳性。** `FGitSourceControlState::IsCheckedOut()` 直接 `return IsSourceControlled()`（GitSourceControlState.cpp:194，tracked 就等于已签出），`UDataValidationChangelist::IsDataValid` 却把它当「本地已改」用（DataValidationChangelist.cpp:161，文案 164 行），于是「被清单里某资源引用、被 git 跟踪、但自己不在清单里」的资源全被判缺失；只查直接依赖（只走一层），报错即 `AllowSubmit(false)`（SSourceControlChangelists.cpp:2564）。本仓库 `git ls-files | grep -E '\.(uasset|umap)$'` 全落在 `Content/` 下（176 个包），故「把整个 `Content/` 放进清单」即可闭合（含 `__ExternalActors__`）。逃逸口：命令行加 `-buildmachine`。
- **`Source/` 换行符本来就是混的，别统一成 LF。** 2026-10-17 实测（`tr -cd '\r' | wc -c`）：CRLF 有 `StellarEra*.Target.cs`、`StellarEra.cpp/.h`、`StellarEraVehicle/*`；LF 有 `StellarEraCore/*`、`StellarEraPlanet/*`、`Cosmos*`、`StellarEra.Build.cs`。`core.autocrlf=true`、无 `.gitattributes`，git 对每个 LF 文件打印 `LF will be replaced by CRLF the next time Git touches it` —— LF 是过渡态，改了会被撤销。易犯：拿 `wc -l` 当 CR 字节数。
- **Git Bash 会把 `/Game/...` 改写成 `D:/Application/Git/Game/...`**，导致 `LogLoad: Error: Failed to enter ...: Failed to load package`，只弹一个标题为 `Message` 的错误框。启动时**不传地图参数** —— `Config/DefaultEngine.ini` 的 `GameDefaultMap` 已是 UniverseMap；确需传就同时 `export MSYS2_ARG_CONV_EXCL='*'`。
